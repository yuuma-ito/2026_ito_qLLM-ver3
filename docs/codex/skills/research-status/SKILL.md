# 研究状況と定期報告

対象リポジトリは `/home/23tc011/2026_ito_qLLM-ver3`。作業前に対象の `AGENTS.md` を確認する。別環境ではリポジトリの所在を確認する。

## 状況の確認

リポジトリで `.venv/bin/python -m scripts.research_status` を実行し、`.cache/research_status/status.md` と `status.json` を更新する。表示だけなら `--dry-run` を使う。これは生成API・通知・Git操作を実行しない。

実行中、要確認、直近の結果を中心に、件数・最終更新・検証レポート・保存設定へのリンクを報告する。確認済みの過去実験はMarkdownから省かれ、JSONには残る。未対応形式や読取失敗は要確認として報告する。要求数の上限は予定レコード数と区別する。

速度と完了見込みは同じ保存設定・同じ実行プロセスの前回観測との比較。初回、再開、件数減少、停滞、停止時に見込みを補わない。要求数が上限の実験では完了時間を断定しない。実行完了、sanity成功、自動検証成功、公開成功を区別する。既存レポートの表示は再検証を意味しない。

## Slack報告の確認・変更

`.venv/bin/python -m scripts.notify_progress --overview --transport email --dry-run` でプレビューする。定期報告の比較履歴は前回のSMTP受理時からの差分であり、Slack着信確認ではない。プレビューや送信失敗で比較履歴を更新しない。

時刻を尋ねられたら `configs/slack_progress.cron` と `crontab -l` の両方、ホストのタイムゾーンを確認する。`--timezone` は本文表示用で、cronの発火時刻はホストのタイムゾーンに従う。変更を依頼された場合は他のジョブを保持して設定ファイルと実登録をそろえ、再読取で確認する。監視側の `--progress-interval` も確認する。

状況確認だけを依頼された場合、通知の送信、追試、実験再開、Git公開は行わない。通知が依頼されている場合は既存のメール経路を利用し、送信失敗を通知済みとして扱わない。`.env`、認証情報、生成コード、任意のエラー本文は一覧や通知に転載しない。

実装・出力項目の説明はリポジトリの `docs/codex/research_status.md` を参照する。
