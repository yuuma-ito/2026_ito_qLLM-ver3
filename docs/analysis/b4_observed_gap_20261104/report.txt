B4の追加成功が多い理由の保存履歴分析（測定禁止修正版）

結論
保存履歴から、差がどこで生じたかと、修正側で失敗が続いた具体的な経過は特定できる。今回、失敗コードを変更できずに繰り返す経路を確認した。一方、その反復が前回コードの提示、診断文、seed規則、実行時期のどれによって生じたかという因果分解は、この観測だけでは確定できない。

対象・検査
共有初期失敗545組×R/F/D/B4の2,180経路を対応づけた。初期コードhash・初期エラー分類の共通性、途中成功後の生成がないこと、生成上限、保存コードhashを照合した。新規モデル要求0、生成コード実行0、再採点0。コードは文字列とASTとしてのみ解析した。本文・既存固定集計・生成履歴は変更していない。
AST一致とはコメント・空白・ソース位置を除いたPythonの構造一致であり、任意入力での意味的同値性の判定ではない。

1. 成功差の所在
追加成功はB4 216、F183、D179、R96。B4対Fは共通130、B4のみ86、Fのみ53、双方失敗276で、純差は33組。
B4対Fのモデル別純差はC7 +23、G3 +15、G4 +3、Q9 +4、Q4 -12。C7とG3の合計+38を他モデルが相殺する構成であり、全モデルでB4が最良という結果ではない。
初期失敗類型別の純差は出力不一致+22、import失敗+8、回路構築失敗+1、IF不適合+2、構文-1、実行時+1、量子ビット数0。33組の差のうち22組は出力不一致層に生じた算術的な差であり、原因の寄与率という意味ではない。
C7のBVだけでB4のみ10、Fのみ0、純差+10。これは差が集中する群の特定であり、10組すべての同じ根本原因を認定したものではない。

2. 修正側の反復・停滞
B4だけ成功した86組のF側では、49組で以前と完全に同じコード、59組で以前と同じASTの再出力が1回以上あった。15組は初回から最後までASTが同一で、60組は全roundのエラー分類が同じだった。これらの分類は重複するので合計しない。
同じ86組のB4側では、以前と同じASTの再出力は1組だった。ただし、成功で選んだ群に失敗側の反復が多いことは因果効果の証明ではない。
B4だけ成功した98組のD側でも56組にAST反復、18組に初回から最後まで同じAST、61組に全round同一エラーを認めた。
全545組ではAST反復を含む経路はF270、D246、B4 3。修正は前回コードを利用する設計なので、反復の少なさだけを性能指標・推奨根拠にはしない。

3. 具体例（目的選択した2例。代表性や因果効果は主張しない）
C7 / T4_BV_011 / seed 6:
Fの初回と追加3回はコードhashがすべて同一で、すべて出力不一致だった。コードは文字列"011"の左端をqubit 0に対応させ、q1とq2を制御にしたオラクルを構成していた。課題はs[0]=1,s[1]=1,s[2]=0を明記し、制御はq0とq1を指定している。B4はround 3でその指定に合うq0/q1のオラクルを生成し、保存された主L3で成功した。この例のFの失敗継続は、ビット対応の誤りを変えないまま同じコードを繰り返したこととして説明できる。保存コードの新規実行はしていない。
G3 / T1_Bell / seed 8:
Fは初回から追加3回まで同じコードhashを返し、毎回cannot import name 'Aer' from 'qiskit'で失敗した。B4はround 1でqiskit_aerからAerSimulatorを読み込む別のコードを生成し、保存された主L3で成功した。少なくともこの例では出力上限ではなく、保存されたimport失敗が修正されなかったことを確認できる。
各コードhashと対応する保存roundはcase_reviews.jsonに記録する。

4. 出力上限説の扱い
Fの終了理由が既知なのは1,368要求中322、Dは1,380要求中325で、いずれも選択された部分追試suffixである。元実験prefixのfinish_reasonは未記録。既知部分のlength終了はF52、D68。これを全体の打切り率へ拡張できない。
B4は1,343要求すべてで終了理由があり、length終了135。ただし群・生成経路の構成が異なるため、これらの率だけでどの条件の出力枠が原因だったかを比較しない。
B4のみ成功したC7/G3のF側42組・126追加要求では、出力が1,024 tokensに到達した要求は0。D側の対応する41組・123要求も0だった。したがって、この主要な差の部分を一律に「説明で出力枠を使い切ったため」と説明する根拠はない。tokens_out==1024は終了理由とは別の代理指標として保存する。

5. 次に因果関係を確かめるための条件（未実施）
同じ失敗コード・課題・モデルdigestを用い、同時期の要求順を均等化し、各条件に対応づけた新seed規則を事前固定する。B4（課題のみ）、F（課題＋前回コード＋診断）、D（F＋説明指示）を比較する。前回コード提示と診断提示の影響を分離するなら、課題＋前回コードのみの条件も必要となる。
要求回数を揃える比較と累積tokens予算を揃える比較を分ける。全要求で終了理由を記録し、失敗・打切りを除外しない。観測結果を見て有利な設定だけを採らない。今回、新規生成やこの追試は開始していない。
